# User guide: resolving `factory:needs-help` issues

Use this guide when Factory pauses an issue because it needs a human answer or
decision before planning or execution can continue.

## What `factory:needs-help` means

`factory:needs-help` is a deliberate pause, not a failure. Factory has posted
an escalation comment that identifies the question, evidence, and recommended
next action. Common reasons are:

- an intake question is unanswered;
- a plan is missing information required for the Definition of Ready;
- a high-risk plan needs human approval; or
- an investigation or review has reached its retry/escalation limit.

Start with the latest Factory escalation comment. Do not guess which question
needs answering if the issue contains more than one escalation.

## The normal answer-and-resume flow

For an information or product decision:

1. Read the latest escalation comment, especially **Observed problem**,
   **Relevant logs/artifacts**, and **Recommended human decision**.
2. Add a new comment answering each question explicitly. Include the decision,
   its scope, and any constraints or exceptions.
3. If the answer resolves the planning question, change the lifecycle label
   from `factory:needs-help` to `factory:needs-plan`.
4. Leave the existing `type:*`, `risk:*`, and any other descriptive labels in
   place.
5. Allow the planning automation to run again. It will read the issue and the
   decision comment, then produce a fresh plan.

The key distinction is:

- `factory:needs-plan` means Factory may plan this issue autonomously.
- `factory:ready` means a reviewed plan exists and implementation may begin.

Do not move an issue directly to `factory:ready` merely because you answered a
question; the planner still needs to produce and validate the plan unless the
escalation explicitly asks for approval of an already-complete plan.

## When the right next label is `factory:ready`

Use `factory:ready` only for an escalation that is explicitly an approval gate,
such as a high-risk plan that is already complete and has no unresolved
questions. In that case:

1. Comment with the approval and any conditions.
2. Verify that the plan is acceptable as written.
3. Replace `factory:needs-help` with `factory:ready`.

If the approval changes the scope, acceptance criteria, dependencies, or
implementation approach, use `factory:needs-plan` instead so the plan is
recomputed.

## Comment template

```text
## Human decision

Decision: <the answer or decision in one sentence>

Scope: <what this applies to>

Constraints / exceptions: <none, or list them>

Accepted plan changes: <what the planner should update>

Evidence or references: <links, issue numbers, documents, or “none”>
```

For several questions, answer them as a numbered list so the planner can map
each answer to the corresponding escalation question.

## What not to do

- Do not silently edit the issue body to hide the unresolved question.
- Do not remove the Factory escalation comment; it is part of the decision
  record.
- Do not add a second conflicting `factory:*` lifecycle label.
- Do not use `factory:ready` to skip planning or approval.
- Do not edit `.factory/plan-result.json` or other worktree artifacts in the
  GitHub issue; those are generated by the workflow.

## Quick checklist

Before resuming an issue, confirm:

- every question in the latest escalation has an explicit answer;
- the decision is clear enough for someone else to apply;
- changed scope or acceptance criteria are called out;
- supporting links or evidence are included when relevant; and
- the lifecycle label is `factory:needs-plan` unless this is an explicit
  approval of an already-complete plan.

The lifecycle transitions and automation ownership are documented in
[`docs/lifecycle.md`](lifecycle.md).
