# Factory workflow inventory

This is a source-grounded snapshot of the issue delivery and release flows. The workflow YAML, automation definitions, lifecycle policy, and Cezar implementation remain authoritative. The end-to-end ownership summary is in [workflow-map.md](workflow-map.md).

## Configured issue paths

| Path | Trigger and implementation | Handoff, evidence, and owner |
|---|---|---|
| Intake | `automations/intake.json` admits opened or newly `factory:new` issues. The hourly `factory-maintenance` schedule also selects one existing intake candidate. `workflows/intake.yaml` selects, classifies, validates, and routes it. | `.factory/intake-result.json` is validated before routing. `scripts/route-intake-or-no-work.ps1` assigns the next state. |
| Planning | `automations/needs-plan*.json` dispatch `workflows/plan.yaml` for `factory:needs-plan`. | The `factory-plan` skill writes `.factory/plan-result.json`; the workflow validates Definition of Ready and routes to ready, needs-help, or done when decomposed. |
| Implementation | `automations/ready-to-implement-*.json` dispatch `workflows/implement.yaml` for ready issues with a complexity label. | The workflow prepares the issue, moves it to working, keeps one implementation session through bounded repair, binds validation receipts to the changed tree, validates the result, and routes success to review or failure to investigation. The implement job owns its PR through merge. |
| Independent review | `automations/ready-to-review.json` dispatches `workflows/review.yaml`. | A separate reviewer session writes `.factory/review-result.json`. The workflow validates the exact PR head and merge eligibility before the router can request the configured merge or route changes. GitHub approval and merge state remain authoritative. |
| Review repair | `automations/changes-requested.json` dispatches `workflows/fix-review.yaml`. | The same PR owner fixes findings, runs governance and targeted validation, and returns the issue to review. It does not create a replacement PR. |
| Investigation | `automations/investigate.json` dispatches `workflows/investigate.yaml` after implementation failure, review-round exhaustion, or a stale-work timeout. | A bounded evidence pass writes `.factory/investigate-result.json`; validated outcomes route to ready, needs-plan, or needs-help. The outcome does not currently carry a durable PR-owner handoff. |
| Delivery tracking | `workflows/maintenance.yaml` runs `scripts/sync-issue-delivery.ps1` before intake and lifecycle sweep. | Non-draft PRs move eligible pre-PR issues to `factory:pr-open`; a merged PR with a closing keyword moves the issue to done. Tracking epics and active/review states are not overwritten. GitHub PR state is the merge evidence. |
| Verification | `workflows/verify.yaml` selects impacted and mandatory checks, invokes them, and evaluates the policy verdict without an agent step. | Selection, results, and verdict are separate `.factory/verification/` artifacts; the verification ledger records the evaluated result. |

The state and outcome table is [policies/lifecycle.json](../policies/lifecycle.json). Intake/stale selection and lifecycle repair are implemented by `scripts/select-intake-issue.ps1`, `scripts/refresh-stale-workable.ps1`, `scripts/route-state.ps1`, and `scripts/sweep-lifecycle.ps1`. The maintenance schedule is intentionally a bounded one-item catch-up, not the complete user-directed backlog ranking policy.

## Execution and authority boundaries

`cezar/packages/cezar/src/automations/github-poller.ts` finds bounded event candidates; `cezar/packages/cezar/src/automations/scheduler.ts` rechecks eligibility and admits/launches candidates; `cezar/packages/cezar/src/automations/event-poll-cycle.ts` records the poll receipt and launch result. `cezar/packages/cezar/src/workflows/load.ts` loads repository and shared YAML definitions, validates their step structure, and lets a project definition shadow a shared one. `cezar/packages/cezar/src/workflows/run.ts` executes the ordered steps and records their events through `cezar/packages/cezar/src/runs/store.ts` (`runs.json` index plus append-only per-run event files).

The Cezar run record and event log are the local execution history. GitHub issue labels are the cross-system lifecycle projection and automation trigger; `policies/lifecycle.json` defines legal transitions and owners. GitHub remains authoritative for issue/PR existence, reviews, and merge state. `routing/automation-catalog.json` declares the intended `cezar` state authority and route-result artifacts, but does not replace those external facts. The current workflow contract is an ordered step list with bounded retries; the code inventory does not show a first-class durable child-workflow graph or fork/join contract yet. That is a proposed extension, not current behavior.

## Review, checks, and release

`workflows/implement.yaml` and `workflows/fix-review.yaml` call the governance guard, targeted tests, and integration verification before successful handoff. `workflows/review.yaml` checks the reviewed SHA and calls `scripts/verify-merge-eligibility.ps1`; the router only merges or requests auto-merge after the gate receipt names the same PR and SHA. `docs/local-validation.md` defines local receipts, and the repository instructions require Linux validation of pushed heads that touch workflow/runtime policy paths.

After merge to `dev`, the Bazzite `factory-local-promotion` timer owns channel activation, full validation, canaries, rollback/quarantine, and stable promotion; `factory-autodeploy` reconciles the host to stable. See [promotion-pipeline.md](promotion-pipeline.md) and [config/promotion-policy.json](../config/promotion-policy.json). The `factory-release-fix-pr` workflow is a submission step for a prepared and validated fix; the originating PR owner still owns delivery through merge. The daily `factory-fixture-lifecycle` automation drives a model-free lifecycle canary against a sandbox repository.

## Existing fixture and observed gap

The lifecycle tests cover both sides of a PR ownership failure, but currently as separate cases: `tests/run-tests.ps1` verifies that an implementation failure routes working to investigate and that a conflicting PR in review routes to changes-requested. The added baseline fixture pairs an issue in `factory:investigate` with its still-open conflicting PR; `scripts/sweep-lifecycle.ps1` does not return that issue to the PR fix owner because only `factory:review` declares `onConflict` in `policies/lifecycle.json`. The issue remains in investigation while the PR remains conflicting. Once investigation routes to ready or needs-plan, a fresh implementation can be dispatched without first recovering ownership of the existing PR.

This is a reproducible gap, not a proposed policy resolution. The repair needs to preserve the original implement/fix job's PR ownership across investigation and recovery. The integration fixture establishes the current behavior so a later owner-link/recovery change can update the expected outcome deliberately. Relevant sources: `scripts/route-state.ps1` (implementation and investigation outcomes), `scripts/sweep-lifecycle.ps1` (PR conflict recovery), `scripts/sync-issue-delivery.ps1` (delivery projection), `policies/lifecycle.json` (state owners and conflict route), and `tests/run-tests.ps1` (baseline fixture).
